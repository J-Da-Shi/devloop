# DevLoop 项目优化评估报告

评估日期：2026-08-23  
评估基线：`ca625bd`  
评估范围：当前仓库的 Server、Web、Desktop、数据库、Git、Runner、Workflow、共享契约、测试与部署配置。

## 1. 结论摘要

DevLoop 已具备一条完整的本地 AI 开发交付链路，不是需要从零补齐核心流程的原型。项目注册、隔离 Worktree、Codex/Claude/Fake Runner、任务 Revision、失败恢复、并发 Worker、结果 Commit、Diff、冲突处理、预览、Playwright、人工审核、Skill 和上下文预算均已有实现和测试基础。

下一阶段不应优先堆叠更多 Runner 或复杂协作概念，而应先解决三类基础问题：

1. **补齐安全边界**：当前身份固定为实例所有者，设备配对和角色数据结构尚未接入；Claude 和预览进程的隔离强度也需要统一。
2. **建立持续质量门禁**：核心后端测试较多，但仓库没有面向 Pull Request 的完整 CI，Web 业务交互和 Desktop 仍缺少自动化覆盖。
3. **控制单机长期运行成本**：列表、事件和产物会持续增长，需要分页、事件追赶、保留策略、配额和可恢复备份。

建议按 P0 安全与质量基线、P1 可维护性与长期运行、P2 产品效率能力的顺序推进。P0 完成前，不建议把“多人共享部署”宣传为应用内原生能力。

## 3. P0：优先建立安全和质量底座

### 3.1 接通身份、设备角色与审计闭环

**证据**

- `apps/server/src/http.ts` 的 `resolveIdentity()` 始终返回 `instance-owner/editor`，请求没有凭据校验。
- `paired_devices`、`pairing_sessions`、`remote_commands` 和 `audit_events` 已存在于 Schema，`DeviceRepository` 也实现了配对、角色调整和撤销，但 Server 路由与 Web 路由没有消费这些能力。
- `audit_events` 当前只有表定义，没有写入或查询实现。
- 服务允许在显式设置 `DEVLOOP_ALLOW_LAN=true` 后监听非回环地址；部署文档依赖 Nginx Basic Auth、IP 白名单或 Tailscale 提供外层访问控制。

这与“默认本地单用户”的产品边界一致，不是当前本机模式的功能错误；但它是多人或多设备使用前必须补齐的能力缺口。

**建议范围**

- 保留本机 owner 快速路径，为远程访问增加短期配对码、设备凭据、HttpOnly 会话、撤销和轮换。
- 将 `viewer/operator/editor` 角色守卫绑定到实际设备身份，明确每个 API 的最小权限。
- 为任务确认、取消、审核、冲突解决、Worker 配置、Skill 发布和项目配置写入审计事件。
- 加入 CSRF/Origin 校验、安全响应头、登录与配对限流，并让非回环监听要求配置应用级访问策略。
- 在设置页提供设备列表、最近访问、角色调整和撤销能力；清理目前未接入的认证样式或将其用于真实页面。

**完成判据**

- 未配对的非本机请求无法读取任务；viewer 无法触发变更；被撤销设备立即失效。
- 每个高风险操作能追溯 actor、时间、对象、结果和幂等键。
- 本机模式仍能离线启动，不强制用户注册云账号。

### 3.2 统一 Agent、验证和预览进程隔离

**证据**

- Codex Runner 使用 `workspace-write` sandbox；Claude Code Runner 使用 `--dangerously-skip-permissions`，两者宿主机隔离语义不一致。
- PreviewService 会在结果 Worktree 中执行锁文件对应的安装命令，并通过 shell 启动预览命令。环境变量已采用白名单，这是正确基础；但进程仍继承 `HOME`、`PATH`，并默认拥有宿主机网络与用户权限。
- Worktree 提供 Git 文件隔离，不等同于文件系统、网络、CPU、内存或进程隔离。

**建议范围**

- 引入统一的 `ExecutionPolicy`，分别描述文件系统、网络、环境变量、资源限额、最大子进程数和超时。
- 优先在容器、Linux namespace 或受控沙箱中运行 Agent、依赖安装、自定义测试和预览；Desktop 可保留显式信任模式作为兼容降级。
- 默认关闭预览外网访问，按项目声明开放；记录实际执行命令、镜像/工具链版本与策略摘要。
- 对依赖生命周期脚本增加项目级策略和明确提示，避免自动验证隐式扩大执行权限。
- 继续保留现有进程组终止与敏感变量过滤，并增加 CPU、内存、磁盘和日志大小上限。

**完成判据**

- 恶意预览脚本不能读取 DevLoop 数据目录、SSH/Codex 配置或其它项目目录。
- 取消、超时或服务关闭后无残留子进程，资源超限能形成可操作的 Run 事件。
- Codex、Claude、自定义 Playwright 和 Preview 使用可比较、可展示的隔离策略。

### 3.3 增加 Pull Request 质量门禁

**证据**

- `.github/workflows/pages.yml` 只负责官网发布。
- 根脚本已经提供 `packages:build`、`typecheck`、`test`、`lint`、`format` 和 `build`，但没有 CI 将它们设为合并条件。
- Node 支持范围是 `>=24 <27`，缺少对支持版本的持续验证。

**建议范围**

- 新增 CI：冻结锁文件安装、packages build、typecheck、Vitest、ESLint、Prettier 和 `git diff --check`。
- 至少覆盖 Node 24 和 26；原生依赖缓存键包含 OS、CPU、Node 和 lockfile hash。
- 将 Web build、Server build 和 Desktop typecheck 作为独立任务，便于快速定位失败层。
- 对主分支启用必需检查，并加入依赖更新和高危漏洞告警；不要用跳过类型检查或删除测试换取绿灯。

**完成判据**

- 任一支持 Node 版本的类型、测试、格式或构建失败均阻止合并。
- CI 从干净环境启动，不依赖开发者机器已有的 `dist` 或 workspace 链接。

## 4. P1：改善可维护性与长期运行

### 4.1 拆分超限模块并引入类型化领域错误

**证据**

- `apps/server/src/agent-worker.ts` 为 1,307 行，混合领取、准备、上下文、Runner、Git、验证、恢复和收尾。
- `apps/server/src/app.ts` 为 1,087 行，集中注册全部 API、冲突任务、预览与 SSE。
- `apps/server/src/preview-service.ts` 为 743 行，混合配置检测、依赖安装、进程生命周期和健康检查。
- `_dashboard.scss` 为 850 行，`_diff.scss` 为 750 行，已超过仓库约定的 700 行上限。
- `mapRepositoryError()` 通过匹配错误消息文本映射 HTTP 状态，新增或翻译错误容易改变协议行为。

**建议范围**

- 按 projects、tasks、runs、skills、worker、events 拆分 Fastify route plugin；路由只解析输入并调用服务。
- 将 Worker 拆为 claim coordinator、workspace preparer、runner executor、validation pipeline、retry checkpoint 和 completion coordinator。
- 将 Preview 拆为配置检测、依赖准备、进程会话和健康探测，保持当前外部接口稳定。
- 按页面/组件职责继续拆分 SCSS，避免重新聚合为另一个全局文件。
- 定义带稳定 `code` 的领域错误，集中映射到 HTTP；测试错误 code，而不是中文消息片段。

**完成判据**

- 所有手写源码文件回到 700 行以内，拆分后关键状态转换与取消语义测试保持通过。
- API 错误响应不再依赖错误文案匹配，Web 可按稳定 code 展示操作建议。

### 4.2 补齐 Web、Desktop 和端到端测试

**证据**

- Web 有 64 个非测试 TS/TSX 文件，只有 2 个 core 单元测试，没有组件测试。
- Desktop 主进程包含 500 行窗口、服务生命周期、导航和权限处理，没有测试。
- 仓库没有自身产品的 Playwright E2E 配置；现有 Playwright 服务用于验证 DevLoop 管理的目标项目。

**建议范围**

- 为任务创建/确认/取消、审核通过/驳回、冲突编辑、预览启动、Skill 发布和 SSE 重连增加组件或集成测试。
- 增加 Fake Runner 端到端冒烟测试，覆盖“创建项目 → 任务执行 → 审核 → 完成”以及失败、取消和冲突路径。
- 将 API 客户端与共享 Schema 做契约测试，防止返回体和前端本地类型漂移。
- 抽取 Desktop 服务生命周期和 URL 导航策略为可测试模块，补充窗口关闭、Server 启动失败与外链拦截测试。
- 引入覆盖率报告，先记录基线，再对新增/修改代码设置增量门槛。

**完成判据**

- 核心交付路径可在 Fake Runner 下无人工操作验证。
- Web 关键 Mutation 的成功、冲突、网络失败、禁用和加载状态都有测试。

### 4.3 增加分页、事件追赶和数据保留策略

**证据**

- Dashboard 和任务接口返回全部项目与未删除任务，Web 看板在浏览器端过滤。
- Run 列表只有 `limit`，没有 cursor；Run 事件详情一次读取全部事件。
- SSE 重连从数据库最多回放 200 个领域事件，回放查询完成后才订阅内存事件总线，缺少显式的无缝追赶协议。
- `domain_events`、`run_events`、审核产物和软删除任务没有统一保留、归档或配额策略；目前只在启动时清理 7 天前的 context scratchpad。

**建议范围**

- 为 task、run、run event、artifact 增加 cursor 分页、服务端筛选与稳定排序；保留小数据量下的简单默认体验。
- SSE 返回可确认的高水位，循环分页追赶到高水位后再切实时订阅；处理回放与实时交界处的去重。
- 配置日志、事件、截图、临时 Worktree 和软删除任务的保留期限与磁盘配额，提供 dry-run 清理报告。
- 增加归档、回收站和恢复；物理删除必须校验 Run、审核结果与 Git 引用，不影响可追溯性。
- 用真实数据量执行 `EXPLAIN QUERY PLAN` 后补索引，不提前为所有筛选组合建索引。

**完成判据**

- 10 万条 Run 事件和数千任务下，首屏查询有界且不会一次把全部数据送入浏览器。
- SSE 断开期间超过 200 个事件仍可完整恢复，事件不丢失且不重复触发业务副作用。
- 达到配额时先告警再按策略清理，不删除待审核或保留中的证据。

### 4.4 完善可观测性、容量和备份恢复

**证据**

- 已有 Pino 日志、Worker 心跳、Run 事件和状态页，但没有服务指标、失败分类趋势、阶段耗时或资源用量。
- TaskRun 保存 Runner 版本和起止时间，不保存 token/费用、上下文压缩结果摘要、CPU/内存峰值或队列等待时间。
- 部署文档提供停机打包 `data` 与 `config` 的手工备份，没有应用内一致性备份、恢复校验或容量视图。

**建议范围**

- 记录队列等待、准备、Agent、验证、修复、审核等待各阶段耗时和失败 code。
- 在 Runner 可提供时记录输入/输出 token 与估算费用，无法提供时明确为 unknown，避免伪精确。
- 提供本地指标页和可选 OpenTelemetry/Prometheus 导出，默认不把仓库名、Prompt 或 Diff 发到外部。
- 健康检查区分 liveness 与 readiness，并展示数据库、磁盘、Runner、浏览器与 Git 能力状态。
- 使用 SQLite backup API 或受控 checkpoint 生成一致性备份；恢复前校验 manifest、Schema 版本、文件校验和与可用空间。

**完成判据**

- 用户能回答“任务为什么慢/失败、队列堵在哪里、磁盘由什么占用”。
- 备份与恢复可自动验证，并有一次文档化的恢复演练结果。

## 5. P2：可增加的产品能力

以下能力有明确价值，但应建立在 P0/P1 基线上。

### 5.1 任务组合与检索

- 全局搜索任务、Run、分支、Commit 和事件，并支持项目、状态、Runner、日期和负责人设备的组合筛选。
- 任务标签、保存的筛选视图、任务模板、批量调整优先级/确认/取消。
- 显式任务依赖和阻塞原因，让 Worker 只领取依赖已完成的任务；第一版保持 DAG，无需引入通用工作流编排器。
- 回收站、归档与只读历史视图，解决软删除后不可见但数据仍占用的问题。

### 5.2 通知与自动化

- Desktop 系统通知：任务完成、阻塞、待审核、冲突和 Worker 降级。
- 可签名 Webhook：只发送稳定事件 Schema 和资源 ID，默认不发送 Prompt、日志或 Diff。
- 安静时段、事件去重和失败重试，避免高并发任务产生通知风暴。
- 在 Webhook 稳定后再考虑定时任务或外部触发 API，并沿用幂等键和角色校验。

### 5.3 代码托管平台交付

- GitHub/GitLab/Gitea 的 PR/MR 创建、链接、状态检查和评论同步。
- 将 DevLoop 验证结果发布为 commit status，但仍保留 DevLoop 人工审核作为写回闸门。
- 支持项目级交付策略：“直接推送任务分支”或“创建 PR/MR”，不自动覆盖受保护分支。
- 展示目标分支最新状态与远端 CI 结果，减少审核通过后才发现外部检查失败。

### 5.4 执行策略与质量画像

- 按项目记录 Runner 成功率、耗时、重试率和验证失败类型，辅助选择 Codex 或 Claude，不做不可解释的自动切换。
- 项目级验证 Profile：必需命令、可选命令、浏览器矩阵、覆盖率阈值和产物保留策略。
- 对 flaky 验证做有限次数、可观察的重跑；保留每次结果，不把重跑后的通过掩盖为首次通过。
- Runner 插件注册表应继续复用统一接口和能力探测，避免在 API 或 Web 中出现特定 CLI 分支。

## 6. 建议实施顺序

| 阶段 | 目标         | 主要交付物                                                    | 退出条件                     |
| ---- | ------------ | ------------------------------------------------------------- | ---------------------------- |
| 0    | 固化基线     | CI、风险模型、关键 E2E 冒烟、文件规模清单                     | 当前行为可重复验证           |
| 1    | 收紧安全边界 | 真实设备身份/RBAC/审计、统一执行策略、远程访问保护            | 非本机访问与子进程权限可验证 |
| 2    | 降低变更风险 | 拆分 Server/Worker/Preview/SCSS、类型化错误、Web/Desktop 测试 | 文件符合约定且契约稳定       |
| 3    | 支持长期运行 | cursor、SSE 追赶、保留与配额、容量指标、一致性备份            | 大数据量和磁盘压力测试通过   |
| 4    | 提升交付效率 | 搜索、模板、依赖、通知、PR/MR、验证 Profile                   | 用真实团队工作流验证收益     |

建议首个迭代只完成阶段 0，并为阶段 1 写出威胁模型和兼容方案。这样能先获得可靠回归信号，再修改身份和执行边界这两类高风险代码。

## 7. 暂不建议优先投入

- **多 Server 水平扩容**：当前 SQLite、单个 `worker_state` 和本地 Worktree 都以单实例为中心。1-10 个本地并发槽位尚未证明不足前，不应引入分布式调度和租约复杂度。
- **完整多租户 SaaS**：会同时改变身份、密钥、仓库隔离、计费、合规与存储模型，偏离本地优先定位。
- **无人审核自动写入目标分支**：会削弱 DevLoop 当前最清晰的安全边界。可以自动生成建议或 PR，但不应绕过冲突和审核校验。
- **自建通用 CI 平台**：DevLoop 应输出验证结果并接入现有 CI，而不是复制矩阵构建、制品仓库和大规模 Runner 调度。

## 8. 推荐验收指标

后续优化不只以“功能完成”验收，建议持续记录以下指标：

- 安全：未授权 API 测试覆盖率、高风险操作审计覆盖率、残留子进程数、敏感路径逃逸测试结果。
- 质量：CI 成功率、增量测试覆盖率、回归逃逸数、超过 700 行的手写源码文件数。
- 性能：任务/Run/事件查询 P95、SSE 重连追赶耗时、队列等待时间、Worker 槽位利用率。
- 稳定性：执行成功率、取消成功率、重试恢复成功率、预览启动成功率、孤儿 Worktree/进程数量。
- 容量：数据库、仓库、Worktree、artifact 各自占用量，清理前后释放量，备份恢复成功率。
- 产品：从创建任务到待审核、从待审核到完成的中位时间，人工冲突处理时间，通知到审核响应时间。

这些指标应默认保存在本地；任何外部遥测都应显式启用并对内容做最小化处理。
